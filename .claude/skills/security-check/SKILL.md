# セキュリティ点検

個人用の小さなアプリを対象にした点検です。目的は「完璧な安全」ではなく、
**取り返しのつかない事故を防ぐこと**。具体的には、APIキーの流出と、意図しない公開の2つです。

この2つだけは、起きてしまうと自分では元に戻せません。キーは第三者に使われ、
公開されたものは誰かの手元にコピーされます。他の項目はあとから直せます。
だから報告の優先順位も、まずこの2つを見てください。

## 進め方

### 1. 機械的な点検を走らせる

```
python .claude/skills/security-check/scripts/scan.py <プロジェクトのパス>
```

ファイルの有無や文字列の一致など、**誰が何度やっても同じ答えになるもの**を
このスクリプトが調べ、JSONで返します。自分で grep して回る必要はありません。

Pythonは、プロジェクトに仮想環境があればそちらを使うと確実です
（例: `.venv\Scripts\python.exe`）。スクリプト自体は標準ライブラリだけで動きます。

### 2. 判断が要る点検を自分で行う

スクリプトには判断ができません。以下は実際にコードを読んで考えてください。
**該当する項目だけ**でよく、使っていない技術の項目は飛ばします。

#### プロンプトインジェクション（LLMを使うアプリ）

利用者が貼り付けた文章・アップロードした画像・外部から取得したデータを
プロンプトに入れている箇所を探します。そこには「これまでの指示を無視しろ」といった
**命令文が混ざっている可能性があります**。AIは指示とデータを完全には区別できません。

見るべきこと:

- その文章はどこから来たか（自分が書いた / 他人が書いた / Webから取った）
- AIの出力で何が起きるか。**画面に表示するだけなら被害は小さい。**
  ファイル操作・コマンド実行・外部への送信につながるなら危険度が跳ね上がる
- 役割の指示（system）と利用者のデータが、同じ塊に混ざっていないか

個人用で、出力を人が読むだけなら、多くの場合「低」で構いません。
**危険度を入力の出どころではなく「出力が何をするか」で判断する**のが要点です。

#### AIの出力の扱い

AIが返した文字列を、そのままHTML・コード・コマンドとして扱っていないか。
スクリプトが `unsafe_allow_html=True` などを検出しますが、
`exec`、`eval`、`subprocess`、`os.system` に渡している箇所は自分で探してください。

#### 入力量と費用の歯止め

- 貼り付けられる文章量に上限があるか。無制限だと、1回の操作で
  無料枠を使い切ったり、有料プランなら課金が走ったりします
- 連打できる作りになっていないか
- 失敗したとき自動で何度も再試行していないか（再試行の回数に上限があるか）

#### 認証と公開

- そのアプリは誰が開ける状態か。待ち受け先がlocalhost以外なら、
  **同じWi-Fiの他の端末から見えます**
- 公開する予定があるなら、認証の仕組みがあるか

#### 依存パッケージの既知の問題

スクリプトは固定状況しか見ません。既知の脆弱性を調べるには、
`pip-audit` や `npm audit` が使えるならそれを使い、使えなければ
主要なパッケージ名とバージョンでWeb検索して確認してください。
**記憶で「このバージョンは安全」と判断しないこと。**

### 3. レポートを書く

結果は必ず次の形で出します。

```markdown
# セキュリティ点検レポート

対象: <プロジェクトのパス>
実施日: <日付>

## 結論

<2〜3文。すぐ直すべきものがあるか、無いか。無いなら「無い」とはっきり書く>

## すぐ直したほうがよいもの

| 何が | なぜ危ないか | どうするか |
|---|---|---|

## 直したほうがよいもの

（同じ形式）

## 知っておくとよいこと

（同じ形式。今は問題ないが、条件が変わると問題になるもの）

## 確認できて問題なかったもの

- <項目>

## 今回見ていないこと

- <点検の範囲外だったもの。なぜ見なかったかも書く>
```

## レポートの書き方

**「何が起きたか」と「次にどうするか」を分けます。** エラーコードや英語の
メッセージを並べても、受け取った人は動けません。かわりに、
「キーが公開される」「同じWi-Fiの人が開ける」のように**結果**で書いてください。

**該当しないものを水増ししない。** 問題が1件もないなら「ありません」と書くのが
正しい報告です。無理に項目を増やすと、本当に危ないものが埋もれます。

**「今回見ていないこと」を必ず書く。** 点検は万能ではありません。何を見て
何を見ていないかが分かって初めて、受け取った人は残りのリスクを判断できます。
見ていないものを黙っているほうが、見落としより害になります。

**危険度は、この環境での実害で決める。** 一般論の重大度ではありません。
1人用でローカルでしか動かないアプリなら、教科書的には「重大」な項目でも
実害が無いことがあります。逆に、キーの流出は個人用でも致命的です。
判断に迷ったら、**「これが起きたら自分で元に戻せるか」**を基準にしてください。

## 直すところまでやるか

レポートは**報告までで止めます。** 勝手に直さないでください。
設定を変えると動かなくなることがあり、何を変えたか分からない状態が一番困ります。

直す場合は、どれを直すかを選んでもらってから、1件ずつ直して都度確認します。

## この点検で分からないこと

正直に書いておきます。以下はこのスキルの範囲外です。

- 実際に攻撃を試す検証（やりません）
- サーバーやネットワーク側の設定
- 使っているサービス（Google、Anthropicなど）側の安全性
- アプリを公開・配布する場合に必要になる、本格的な認証や権限管理

個人がローカルで使うアプリとして「事故を起こさないか」を見るもの、
と理解してください。公開するなら、別途きちんとした検討が要ります。
